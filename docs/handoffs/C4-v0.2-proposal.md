# C4: structured run association and budget sessions for table-manners v0.2

Status: Wafflery-owned proposal for the contract owners before v0.2 is tagged, 2026-10-31.
Not a change to v0.1 and not an accepted schema. [Current evidence](../integration-sources.md).
An accompanying PROPOSALS.md patch is prepared in this directory; the sibling checkout is
read-only in this session. No shared schemas or tool implementations have been changed.

## Problem and scope

Both current servers put a run resource in progress `message`, using different human formats.
Cancellation returns no MCP call response. A client cancelling before a final result cannot
reliably identify the terminal resource. Both tool budgets reset with their server process;
clients need to recognize that boundary without guessing or silently renewing allowance.

Keep MCP revision **2025-11-25** and the existing per-process budget model. No durable billing
ledger, automatic job recovery, automatic retry, new task protocol or roots migration is proposed.

## Proposed wire additions for owner/schema review

Use MCP's existing `_meta` extension container rather than a new ad hoc progress member. The
inspected rmcp 3.8.0 `ProgressNotificationParam` already exposes notification metadata. Final
metadata key names and shared schema placement must be approved by table-manners.

### Request correlation and run association

The client supplies a unique progress token and an optional UUID-like opaque correlation string:

```json
{
  "_meta": {
    "progressToken": "host-attempt-123",
    "table-manners/client_run_id": "host-attempt-123"
  }
}
```

Once a run exists, the first progress notification, and every subsequent notification, carries
this proposed metadata in addition to ordinary increasing progress and human `message`:

```json
{
  "_meta": {
    "table-manners/run": {
      "id": "tool-run-7",
      "resource": "example://run/tool-run-7/run.json",
      "session_id": "server-session-9",
      "client_run_id": "host-attempt-123"
    }
  }
}
```

Add `run.session_id` and `run.client_run_id` to terminal results and the corresponding fields
to run-list entries in the v0.2 schemas. Use null when not applicable (e.g. no client correlation
or a non-server CLI run); never fabricate session continuity. Persist association when creating
the run before paid work. A session must reject reused non-null correlation IDs before another
execution; this is not a promise of cross-process exactly-once execution or cached replay.

A client may match a run-list entry only by the explicit session/client correlation pair,
never action/time/filename similarity. A paginated list might not yet contain the run; absence
does not prove no work or spend. Pre-allocation cancellation may still leave no run: report
unknown outcome, do not create a fictional success/failure. Metadata/result mismatches are errors.

### Observable server budget session

Define a required resource for servers, `<tool>://session`, listed in their resource declarations:

```json
{
  "id": "server-session-9",
  "started": "2026-10-31T12:00:00Z",
  "budget_usd": 5.0,
  "spent_usd": 0.5,
  "reserved_usd": 0.1,
  "remaining_usd": 4.4
}
```

The resource's exact schema is part of this proposal. Define finite nonnegative numeric fields;
use a documented null budget/remainder for an uncapped/free session rather than inventing a
money limit. Remaining is the available cap after reported spent/reserved; specify rounding
tolerance with the existing spend schema. Read it atomically without paid work. The ID is fresh
on server start and any ledger reset. A config reload that resets budget must change the ID.

Give estimate results a shared session/budget observation (same schema/identity), outside private
tool result bodies, so C1's estimate mapping can bind inputs/cap to the observed session. Agree
that precise placement with C1; do not force the host to parse Rascal/Squint private budget names.
Tool enforcement remains authoritative when remaining budget changes after an estimate.

Squint already writes estimate runs and currently serializes those requests. This is allowed;
the host labels its own estimate requests as controls and does not adopt them as user attempts.
Define the scheduling contract explicitly: estimates may be serialized; resource reads needed
for status/cancel/session observation must remain responsive while work runs. No estimate action
may itself incur provider spend. Final metadata maps an estimate to its session even if it has
its own run ID.

## Host behavior and minimal recovery

Any observed session change invalidates estimates and is shown as a new budget session.
Wafflery never restarts a child automatically to refill budget. A deliberate restart may
begin the tool's configured allowance again, clearly disclosed; this is not a daily spending cap.
Unknown spend on an interrupted old session remains unknown rather than becoming zero.

Under v0.1, Stop before a result normally produces **Cancellation requested; final outcome
unconfirmed**. Keep the execution reservation while the child may still be active. This is an
expected incomplete-information state, not a red execution error or a trigger to resubmit.
Only approved v0.2 association allows following the exact resource without parsing message text.

## Fixtures and acceptance

Provide paired tool examples/schema cases for: correlation accepted/reused/mismatched; first and
later progress metadata; cancellation before/after run allocation; cancelled call with no reply
but terminal resource; no resource yet; session restart/config reset; estimates with session
identity; reserved budget moving during a run; resource reads while the execution permit is held.

Use table-manners' existing Squint cancelled fixture as a reference for v0.1 terminal shape and
the contract text as authority. Do not invent a Rascal cancelled fixture and claim it came from
Rascal. Tools retain their own independent clients; Wafflery adds host-side no-duplicate and
unknown-outcome fixtures. No live paid calls are required to validate these semantics.

This proposal asks for a concrete v0.2 schema decision now. It does not claim to be sufficient
for C1 readiness, C2 native persistence or C3 report framing, which remain separate agreements.
